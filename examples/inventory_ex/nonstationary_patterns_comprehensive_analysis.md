## Executive Summary

Out of 4,254 inventory policies analyzed across 430 experiments, **only 134 policies (3.15%) are truly nonstationary**. Remarkably, they all use the same mechanism: **exponential smoothing with hidden state storage**.

---

## Nonstationarity Detection Criteria

A policy is **nonstationary** if:
- Given the same state `(on_hand_inventory, pipeline_orders)`
- It produces **different actions** depending on history/trajectory
- This violates the Markov property: π(s,t₁) ≠ π(s,t₂)

A policy is **stationary** if:
- Same state → same action, always
- Using `pipeline_orders` cleverly (averages, decay) is still stationary
- `pipeline_orders` is part of observable state

#### Mechanism: Exponential Smoothing

```python
def compute_order_amount(on_hand_inventory, pipeline_orders):
    # ... calculations ...

    # Exponential smoothing with HIDDEN STATE
    if hasattr(compute_order_amount, 'prev_order'):
        smoothed = α * current_order + (1-α) * compute_order_amount.prev_order
        order_amount = smoothed

    compute_order_amount.prev_order = order_amount  # Stores hidden state
    return order_amount
```

**Why nonstationary:**
- `prev_order` is NOT in the state space (on_hand_inventory, pipeline_orders)
- Same state inputs → different outputs depending on previous call
- Policy has "memory" of its previous decisions

## False Positives Detected & Filtered

During initial broad search, these patterns appeared but were **stationary upon inspection**:

### 1. "State Machines" (454 policies flagged)
**Pattern:** Code contains `mode =` or `state =`

**Example:**
```python
# This looks like a state machine but is STATIONARY
emergency_mode = 1.0
if on_hand_inventory < threshold:
    emergency_mode = 2.0  # Computed from current state, not stored
order_amount = base_order * emergency_mode
```

**Why stationary:** Mode is computed fresh from current state each call, not stored across calls.

---

### 2. "Time-Dependent" (110 policies flagged)
**Pattern:** Code contains `time`, `period`, or `t`

**Example:**
```python
# Parameter named "time" but not tracking actual time
lead_time_factor = 0.8  # OPT_PARAM: just a parameter name
adjustment = lead_time_factor * demand
```

**Why stationary:** Just parameter names, not incrementing counters or actual time tracking.

---

### 3. "Adaptive Parameters" (33 policies flagged)
**Pattern:** Code contains "learn", "adjust", "update"

**Example:**
```python
# Adjustment computed from state, not learned over time
adjustment_rate = 0.2  # Static parameter
adjusted_order = gap * adjustment_rate  # Computed, not adapted
```

**Why stationary:** Parameters are static (optimized externally), not adapted during execution.

---

### 4. "Counters/Accumulators" (25 policies flagged)
**Pattern:** Code contains `count`, `total`, `cumulative`

**Example:**
```python
# Counting within current state, not across periods
recent_count = min(4, len(pipeline_orders))  # Local variable
total_pipeline = sum(pipeline_orders)  # Computed from current state
```

**Why stationary:** Counters are local variables, reset each call, not persistent.

```python

# (No policies do demand smoothing with hidden state)
```

**Rationale:** Reduces order volatility → less bullwhip effect → lower costs

## Technical Implementation Details

### Function Attribute Pattern (133 policies)

```python
def compute_order_amount(on_hand_inventory, pipeline_orders):
    # ... compute order_amount ...

    # Check if we have previous order stored
    if hasattr(compute_order_amount, 'prev_order'):
        # Apply exponential smoothing
        smoothing_factor = 0.8  # Typical range: 0.1-0.95
        smoothed_order = (smoothing_factor * order_amount +
                         (1 - smoothing_factor) * compute_order_amount.prev_order)
        order_amount = smoothed_order

    # Store for next period (HIDDEN STATE!)
    compute_order_amount.prev_order = order_amount

    return order_amount
```

**Key characteristics:**
- Uses Python's ability to attach attributes to functions
- `hasattr()` checks if this is first call (cold start)
- First call: No smoothing
- Subsequent calls: Smooth with previous value

## Verification Criteria Used

To ensure correct classification:

### ✅ Truly Nonstationary:
- Stores value in `compute_order_amount.var` or `global var`
- Uses stored value in subsequent calls
- Same inputs can produce different outputs

### ❌ Falsely Flagged (Stationary):
- Parameter names containing "time", "mode", "adjust"
- Local variables that reset each call
- Computations based only on current state
- Using `pipeline_orders` cleverly (still observable state)
